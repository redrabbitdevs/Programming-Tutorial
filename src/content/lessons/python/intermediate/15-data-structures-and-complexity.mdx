# Data Structures & Big-O Complexity

Code that handles ten items instantly can crawl on ten thousand. **Big-O notation** describes how a piece of code's work grows as its input grows, and knowing what common operations cost on lists, dictionaries, and sets is what lets you pick the structure that keeps your program fast.

## What Big-O measures

Big-O names the *shape* of growth: it ignores constants and small inputs and keeps only the dominant term. **O(1)** — "constant time" — means one step no matter how large the input; `len(my_list)` and a dictionary lookup by key don't get slower as the collection grows. **O(n)** — "linear time" — means work proportional to size: scanning every item. **O(n²)** — "quadratic time" — means work that multiplies: for each of n items, doing something O(n) itself. On large inputs the gap is decisive: doubling the input doubles an O(n) job but quadruples an O(n²) one.

The costs you will use most often:

| Operation | list | dict / set |
|---|---|---|
| Membership test (`x in ...`) | O(n) | O(1) |
| Look up by key | — | O(1) |
| Index by position | O(1) | — |
| Append / add | O(1) | O(1) |

## Why membership costs differ

A list has no index over its values, so `x in my_list` walks the items one by one until it finds a match or runs out — that is O(n). A dictionary and a set compute a **hash** for each key: a fast numeric fingerprint that points straight at the entry's location. The lookup does essentially the same amount of work whether the collection holds 10 keys or 10 million, which is why both are O(1) for membership and key access. That single difference — hash or no hash — explains most "why is this slow?" answers in Python.

This sample deduplicates a list two ways:

```python sample=py-028-dedup-list-set
raw = [3, 1, 3, 2, 1, 4]

seen = []
for value in raw:
    if value not in seen:
        seen.append(value)
print("list-based:", seen)

unique = set(raw)
print("set-based:", sorted(unique))
```

```text
list-based: [3, 1, 2, 4]
set-based: [1, 2, 3, 4]
```

Both produce the unique values, and they differ in two ways worth noticing. The list version preserves first-seen order (the set does not — hence `sorted(...)` to make its output stable), and their costs diverge badly as input grows: the list's `value not in seen` check is an O(n) scan repeated n times, so the whole loop is O(n²); building a set is one pass, O(n). On six items you cannot feel it. At 100,000 items it is the difference between a program that finishes and one that doesn't.

## Recognizing quadratic patterns

The classic O(n²) shape is a **nested loop** — for each item, do something that touches every item. Here is the standard "find all pairs with a given sum" problem:

```python sample=py-029-pair-sum
numbers = [2, 7, 11, 15, 4]
target = 9

for i in range(len(numbers)):
    for j in range(i + 1, len(numbers)):
        if numbers[i] + numbers[j] == target:
            print(f"{numbers[i]} + {numbers[j]} = {target}")
```

```text
2 + 7 = 9
```

The inner loop runs once per remaining item, so the pair checks total about n²/2 — for n = 5 that is 10 checks; for n = 10,000 it is roughly 50 million. The algorithm is correct and often good enough; the skill is *recognizing* the shape before you profile, so you know a slow run on big data has an expected cause rather than a mystery one.

<Callout type="tip">Pick the structure around your access pattern: keep order or index by position → list; look up by name or key → dict; test membership or track "have I seen this?" → set. Matching structure to access pattern is where most performance wins come from — before any algorithm change.</Callout>

## Common mistakes

- **Confusing Big-O with measured speed**: it describes growth as input grows, not milliseconds. A well-written O(n) routine can beat a clumsy O(n²) one on small inputs; Big-O only promises what happens at scale.
- **Assuming `in` is fast everywhere**: it is O(1) on dicts and sets but O(n) on lists. When membership tests dominate your loop, move the collection into a set.
- **Nested loops over two large collections**: usually O(n²). Often one side can become a dictionary, collapsing the inner loop to an O(1) lookup per outer iteration.
- **Fixing structure but not algorithm**: a dictionary makes lookups O(1), but it cannot rescue code that does O(n) unrelated work per item. Measure where time actually goes before restructuring.

## Summary

- Big-O keeps only the dominant growth term: O(1) constant, O(n) linear (doubling input doubles work), O(n²) quadratic (doubling input quadruples work).
- Membership and key lookup are O(n) on lists but O(1) on dictionaries and sets, because hashing points straight at an entry.
- A nested loop over the same data is the signature O(n²) pattern — recognize it before profiling, not after.
- Choose the structure by access pattern: order and positions → list, key lookup → dict, membership and uniqueness → set.
